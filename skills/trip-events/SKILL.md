> 调用方式：能直接调用 MCP 工具就直接调；工具列表里没有它时，在终端运行 `tripcore run 工具名 '{"参数": 值}'`，不确定参数先 `tripcore help 工具名`。规则不变：事实只来自工具或用户，修改先经用户确认。

## 什么时候查

- 目的地和**日期都确定**之后（日期没定先 `set_dates`；活动只在特定日期举行，没有日期没法判断）。
- 用户问“那几天有什么活动 / 演唱会 / 比赛 / 灯会”，或者让你“按时间特色推荐”。
- 排好景点之后可以顺口问一句要不要看看那几天的特色活动，**不要没问就加进行程**。

## 怎么查（只用能联网搜索的工具，不凭印象）

1. 用 `web_search` / `web_fetch` 查“目的地 + 具体日期范围 + 演唱会 / 体育赛事 / 展览 / 灯会 / 节庆 / 美食节”，按用户关心的类型分开搜。国内优先官方渠道（场馆官网/公众号、赛事官网、大麦/猫眼等售票页、文旅局发布）。
2. 只保留**日期落在行程里**的。每条必须有：名称、日期、开始/结束时间、场馆、**来源网址**。缺任何一项就不推荐，不要写“应该有”“一般会办”。
3. 境外目的地：联网查之前先征得用户同意，只用地名和日期关键词搜，不发用户的任何坐标或个人信息。
4. 结果列给用户挑，每条一行：日期时间、名称、场馆、来源。**不要替用户决定要不要去，也不要订票、付款**；票务只告诉用户去哪个页面买。
5. 活动会改期、取消、售罄：告诉用户“这是某月某日查到的，出发前请再确认”。

## 用户选中之后

1. 用 `lookup_coords`（场馆名）查坐标，不能自己编；查不到就问用户。
2. `add_event(name, lat, lon, date, start, end, source_url, kind, venue, confirmed)`：用户明确说要去才传 `confirmed=true`，否则先作为候选。有票价就同时给 `ticket_price` 和 `ticket_source`。
3. `schedule_days` 重新分天：活动只会排在它举行的那一天；再 `check_plan` 看赶不赶得上、和前后景点有没有冲突（到场晚于开始时间、结束后赶不回住处等），把结果如实告诉用户，由用户决定怎么调。
4. 活动当晚的晚餐、回住处的交通可以接着用 `suggest_food`、`refine_routes` 看。

## 不要做

- 不编活动，不凭印象推荐；查不到就说没查到。
- 不把没有来源网址的活动加进行程；`add_event` 本身也会拒绝。
- 不替用户订票或付款。
